# Incident-derived rules

> Moved from `policy/` on 2026-11-06. References to `.core/run_log.json`, `expect.json`, `Healix.md` and `NFL.md` are to the predecessor repository and do not resolve here; `quality_gate.py`, `run_log.py` and `tests/test_product.py` resolve inside `revision-16-with-regression-test/`.


**How this was built.** Version 1 of these rules was authored top-down from the doctrine. This version is derived: every clause below is a pattern that occurs in *both* product documents (`Healix.md`, `NFL.md`, read 2026-10-23) and in both code trees, with where each instance is stated. A pattern held by one product only is not a company rule; the seven such patterns are listed at the end as the enforcer's own obligations, which every target inherits by running under Healix. The former failure catalogue (families A–K) is not a separate section: each family is the negation of one pattern and sits in that pattern's "refuses" column. This is SYNTHESIS applied to the contract itself; an amendment enters only by the incident rule in §4.

Healix reads this file and cannot write it. A change is a reviewer event, dated, prospective only, never altering an existing decision.

Shared by both products; the enforcer applies them.

## 3. The enforcer's own obligations (single-instance; every target inherits them)

These occur in `Healix.md` only, because they are what the loop is, not what a product claims. A target gets them by running under Healix; a target that keeps its own copy (version 3's `run_log.py`, the core half of `quality_gate.py`) is in violation of rule 13. The cutover of a target is specified once, in `Healix.md` Appendix A; a product document cites it. Status words (PASS, BUILT, PARTIAL, MISSING) are the enforcer's and are defined once, in `Healix.md`.

| Obligation | Healix |
|---|---|
| **Promotion.** A reading becomes a law only by a reviewer `decision` event; the loop never promotes its own readings; an unruled law is refused. | Decision 1 |
| **Evidence sets.** Every typed REJECTED carries the hashes it was earned from; re-litigation is refused while the set is intact; the close reopens as a run log event when any hash changes; a new session receives evidence and lineage, never conclusions. | Decision 2 |
| **Consumer.** A diagnostic is frozen only with the acceptance that will read its answer; an unconsumed read closes IMPLEMENTATION; `reads_without_consumer` is on the health line. | the team level |
| **The parent grades the child.** An acceptance that edits the quality gate, the tests or a generator is graded by the quality gate at its lock; the lock advances only on the parent's PASS. | the play-call level |
| **Mutation and branch counts.** The quality gate is mutation-tested so a surviving mutant means a canary does not bite; injected sets print the count of every branch, and a zero is a finding. | the play-call level |
| **The family harness.** The fourteen refusals above are injected into copies of real cycles with nulls alongside; detection and false-alarm rates per family are published on the health line; stale rates read INSUFFICIENT. | the player level |
| **The reviewer is not the courier.** The author runs the quality gate in a sandbox where the quality gate, run log, objects and Reality store are deny-written; the reviewer's round is four derived lines. | the touch level |

## 4. How these rules change

A rule is added only from an incident: a failure the enforcer passed and Reality, certification or a later audit caught. It is added under a new rules hash, prospectively, with the incident's run log row as its evidence; no cycle already judged is re-judged against it; nothing is added by argument. Rule 7's second clause ("against something other than itself") is the first trip: NFL v3 the predecessor-index mismatch. Three later incidents are recorded and not yet promoted: no per-stage timing on the run log, finished fits that never reached disk, and a cache key that hashed less than the stage consumed. Each lives as an NFL rule (R11, R10, R9) until a second target shows the same need; then it enters §3 and the check protocol gains the line it requires. A rule is removed only when both products are shown, by a read with a consumer, not to need it; none has been.

## 5. What a product must declare to be graded

The check it is judged by, and that check's canaries (7); the required cells and the bar, declared after precision is printed (2); the parent and the chance model (1); the identities that must conserve, in the substrate's own terms (5); the data available before kickoff (10); the population every mechanism was measured on (6); the phenotype, or a statement that none exists and which claims are therefore unmeasurable (4, 11); and the truth the loop did not generate, where it lives and who may read it (9).
