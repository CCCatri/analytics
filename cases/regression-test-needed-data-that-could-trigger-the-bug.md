# A regression test needed data that could trigger the bug

**The surprising result.** For eight revisions, twelve construction tests passed, the quality gate ran end to end, and the sampler converged - while the fitted season chain was mis-linked. Two programs disagreed on whether counting started at 0 or 1, so every predecessor code pointed one pair off. Nothing failed, because the generated league the tests ran on could not express the fault: its ids were season-prefixed, 160 of 168 pairs had no predecessor at all, and a mis-linked pair's state there is just another draw from the same prior. In my words at the time: "Over 8 revisions, 2 programs couldn't agree on if counting started at 0 or 1. Every check passed silently because the model was only compared to itself."

**How it surfaced.** Not through a test. At revision 9 every sub-model failed at one observation, the same index across chains and starts - data-determined, not noise. The standing rule was a check before a fix ("Every lie, blatant or by omission, is resolved before a change is tested; never test an incomplete change"), so a preflight was built that named the failing pair: pair 996, predecessor 497 - the pair coded one before the true predecessor. Revision 10 had checked that every index was in range and missed it; range is not meaning.

**The decision.** Every fit made under the defect was declared unusable and deleted; no persistence estimate was read from them. The check that each predecessor code resolves to the same player's earlier season was added (meaning, not range). Then the test suite was made able to see the class of fault: the league was rebuilt to carry every irregularity the code branches on, and an injected 0-based predecessor was required to be refused by all six programs before the suite counted - the oracle test. The suite was hashed and locked so the quality gate stops before real data when the suite has changed. The grounded status of the revision-8 passes, in hindsight: unverified, not passing - "the chain runs" was all they had shown.

**What the replay shows today (`run.sh` stage 3, 2026-11-05).** Revision 12, before the oracle: its own tests pass, with no injected predecessor fault present. Revision 16, with the regression test: `PASS oracle: ... an injected 0-based predecessor is refused`. Revision 16 also carries two failures of its own (`sample_gain` missing an argument; `gain_sack` INSUFFICIENT_DATA on the synthetic league), unrelated to the predecessor index and not claimed fixed; `checks/test_incident_baseline.py` requires exactly those two by name, so a new failure or a vanished one fails the run. Its handoff had predicted 16 of 16 unchanged without running them - a prediction is not a result until the run that tests it is in the record.

**What this shows and what it does not.** A test can exist, pass, and prove nothing about the condition it was meant to guard, when its fixture cannot reach that condition; the fix for that is not a better assertion but data that can trigger the bug, and an injected instance of the bug's class that must fail before the suite counts. Limits: the before-fix state cannot be replayed (no copy of revisions 1-10 exists; the revision notes are summarized in `INCIDENT.md`); the oracle league did not carry into the current engine and lives only in the revision-16 folder; the rubric's graded examples A-E have been graded by no reviewer other than me; the evaluation-order defect noted in the policy's incident list is a different incident and is not replayed here.

**Roles.** I made the revision-8 decision that was wrong, and the revision-9 call to build a check before a fix; I set the rule that a check counts only where its data can express the fault, which became clause 7's second half in `policy/incident-derived-rules.md`; the agents wrote the preflight, the meaning check and the oracle against those rules, and the replay runs on my machine.
